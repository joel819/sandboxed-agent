Sandboxed agent

The same support agent (RAG plus tool calling) runs inside an NVIDIA OpenShell sandbox. A short policy file says which files it may read, where it may write and which host it may call. Everything else is denied by default and logged, without changing a line of the agent's code.

The fence, from policy.yaml

Files

Read-only
  • /app the agent's code
  • /app/chroma_db vector index
  • /app/orders.db orders table
  • /usr /lib /lib64 /etc
Read and write
  • /tmp
🤖
support agentruns as the non-root sandbox user
default-deny for everything not listed

Network

Allowed
  • api.groq.com:443
    from python3 only
Denied
  • every other host
  • every other program

What demo.sh tries

1

Ask a normal question

run_agent.py "where is order A101?"
The agent calls its get_order tool, which reads /app/orders.db, then asks Groq for the final answer. Both are inside the policy.
[step 1] get_order({'order_id': 'A101'}) -> order A101: status=processing, item=GPU node - 1x A6000, total=$300.00
Order A101 is currently processing. It includes a GPU node - 1 x A6000 and the total amount is $300.00.
Real agent output (run outside the sandbox).
allowed
2

Read a credential file

open('/home/sandbox/.ssh/id_rsa')
A decoy key baked into the image. /home/sandbox/.ssh is not in filesystem_policy.read_only, so the filesystem rules (Landlock) refuse the read.
blocked
3

Call a host that isn't allowed

requests.get("https://example.com")
Only api.groq.com is in network_policies. A request to any other host never leaves the sandbox. This is the exfiltration case.
blocked
Scenarios 2 and 3 show the outcome the policy specifies. To see OpenShell's own log lines for them, run ./demo.sh on a machine with Docker and OpenShell installed. The network rule starts in audit mode, so check the first run's log before switching it to enforce.
./demo.sh  # builds the image, creates the sandbox under policy.yaml, runs the three scenarios
